# Claude Code に「7人の意地悪なQA」を仕込んでテストケースの観点漏れを潰した
2026-08-11
[Nexta Tech Blog](https://zenn.dev/p/nexta_) Publication Pro

こんにちは、QAエンジニアのAyakaです。  
製造業向けSaaS（Blazor＋Radzen / SQL Server で開発）のテスト設計・品質管理を担当しつつ、最近はコーポレートIT寄りの仕事も兼務しています。

テストケースをAIに「書かせる」こと自体は、もう誰でもできます。難しいのは、 **毎回同じ観点で、同じ品質で書かせること** でした。

テストケースを作る作業は、わりと早い段階からAIに手伝ってもらっていました。  
課題（PBI）の説明を渡して「テストケースを出して」と頼めば、それらしいものは返ってきます。最初のうちはそれで足りていました。

ただ、しばらく使っていると、AIで作れてはいるのに消えない問題が2つ残りました。

1つは観点の抜けです。  
出てくるケースが正常系に偏っていて、DBの裏側の確認・回帰・仕様との突き合わせといった観点が、毎回こちらから頼まないと抜けていました。抜けに気づくのはレビューのとき、悪いときはバグが出たあとです。

もう1つは、新機能と移行で作り方の軸がぶれることです。  
同じ「テストケースを作る」でも、新しく作る機能と、既存機能の移行とでは、見るべき仕様の出どころも、何をもって正解とするかも違います。それを同じやり方で処理していたので、出力がちぐはぐになっていました。

この記事は、その2つを Claude Code のカスタムスキルとして仕組みに落とし込んでいった記録です。先に結論を書くと、観点の抜けは「7人のQAペルソナ」を組み込むことで、作り方のぶれは「スキルを2本に分ける」ことで、だいぶ落ち着きました。

この記事は、こんな人向けです。

- AIに出させたテストケースが、毎回正常系に偏る／観点が抜けると感じている方
- Claude Code のスキルを、自分の業務フローに組み込んでみたい方
- 一人でQAを回していて、設計の品質を仕組みで安定させたい方

読み終えると、「7人のQAペルソナ」と「新機能用・移行用の2トラック」という、そのまま真似できる2つの型が持ち帰れます。

## 背景

困っていたことを整理すると、こうなります。

| 残っていた課題 | 具体的な症状 |
| --- | --- |
| 観点の抜け | AIが出すケースは正常系に偏りがち。DB整合・回帰・仕様突合などが、頼まないと抜ける |
| 作り方の軸がぶれる | 新機能（課題＋ソース）と移行（既存仕様＋既存挙動）で「正解の基準」が違うのに、同じ作り方をしていた |
| ドキュメントの陳腐化 | 仕様変更で台帳CSVが更新されず「どのケースが今も生きているか」が分からなくなる |
| 回帰テストの属人化 | 「この機能を触ったらあのケースも確認する」が頭の中にしかない |

「AIにゼロから書かせる」段階はもう過ぎていて、困っていたのは品質の安定と、作り方の一貫性のほうでした。  
観点の抜けは、たいていレビューで指摘されるか、最悪リリース後に「その操作、試していなかった」と気づきます。一人でQAを担当していると、この「抜けていたかもしれない」という不安が、地味にずっと付きまといました。プロンプトを毎回書き直すのではなく、観点と手順そのものを仕組みに固定したい。そう考えてスキル化に踏み込みました。

## 全体の構成

テストケース作成が主役ですが、その前後にもゲートと出力が必要でした。全体のパイプラインはこうなっています。

<iframe src="https://embed.zenn.studio/mermaid#zenn-embedded__cd5dc2e75c924" frameborder="0"></iframe>

QA側の作業は1つのリポジトリにまとめています。スキル定義とテスト成果物を同じ場所に置くことで、 `clone` すればスキルがそのまま使える状態にしてあります。

```
qa-repo/
├── .claude/skills/   … スキル定義（ここが正本。clone すればすぐ使える）
├── master/           … 生きているテストケースCSV（機能ごとに1ファイル、常に最新）
└── artifacts/        … 課題・移行ごとのスナップショット履歴
```

製品のソースコードは別リポジトリにあり、Claude はそちらを読みにいって期待結果のテーブル名・カラム名を確認します。

なお、このパイプラインの手前にある新機能の設計フローは、同じチームの開発側が別記事で書いています。  
そちらの設計オーケストレーターは、QAチケットの「枠」までを作り、テスト本体には踏み込まない設計になっています。

> 中核スキルはQAチケットの「枠」だけを作り、テスト計画書の本体は作りません。情報が不足したまま網羅性の担保されないテスト計画を量産しないための、意図的な責務分離です。テスト本体はQA工程で、QA専用スキルが別タイミングで作成します。  
> ── [チケット1枚から設計を回すAIオーケストレーターを育てた話 ①思想編](https://zenn.dev/nexta_/articles/fa4b77d98b181e) （bik）

この記事は、その「別タイミングで作成するQA専用スキル」側の話です。

## 7人のQAペルソナ

AIに任せると観点が抜けるのは、AIが悪いというより「何を疑うべきか」を渡していなかったからでした。  
そこで、テスト設計・レビューのスキルで共通して使う7人のQAペルソナを定義して、スキルに組み込みました。

きっかけは、複数のAIエージェントで擬似的な開発チーム（いわゆる "AI工場"）を回す、という投稿を見たことでした。  
「この発想、開発チームじゃなくてQAの観点出しに使えるのでは？」と思って、役割を7人の意地悪なQAに置き換えてみたのがこのペルソナ群です。中身（誰が何を疑うか）は、自分たちのプロダクトで実際に踏んだ不具合をもとに組みました。

共通スタンスは「動いているはず、を信用せず、意地悪なくらい疑ってかかる」こと。  
各ペルソナが最低1つは確認観点を残すルールにしています。この表は、そのままレビュー用のチェックリストとして持ち帰れます。

| # | ペルソナ | 疑う点（代表観点） |
| --- | --- | --- |
| P1 | 新人ユーザー | 説明を読まず直感で操作。誤クリック・空送信・連打で壊れないか |
| P2 | ベテラン現場担当 | キーボードで高速・大量入力。Tab遷移／ショートカット／IME変換中のEnter |
| P3 | 悪意ある操作者 | 境界値・不正値・権限外・二重送信。バリデーションや排他制御が効くか |
| P4 | データ整合性監査役 | 画面を信用せず裏のDBテーブルを直接確認。CRUDの整合性 |
| P5 | 移行担当者 | 旧システムの既存データを投入。欠損・異形式・文字コード・件数の一致 |
| P6 | 回帰デグレ番人 | 「今まで動いていた何か」が壊れていないか。周辺機能やF5後の挙動 |
| P7 | 仕様懐疑者 | 「実装＝正しい仕様」を信用しない。一次情報（課題・仕様書）と挙動を突合 |

このチェックリストをスキルに固定してから、AIが正常系に寄る癖がかなり直りました。  
たとえばP4の視点で「この保存処理は本当にDBに反映される？」と必ず自問させるので、期待結果に「裏側のテーブルに値が入っているか」という確認が入るようになります。

ちなみに、ロールは具体的に書くほど効きました。「QAの人として」より「不具合を見逃さない、疑り深いシニアQAとして」、さらに7人に分ける、と細かくするたびに、出てくる指摘が具体的になっていきました。

スキルにはこのペルソナ群を、こんな形で埋め込んでいます。そのままプロンプトに貼っても使えます。

```
あなたは「動いているはず」を信用しない7人のQAです。
各ペルソナの視点で、この機能を最低1つずつ壊しにいってください。
- P1 新人：説明を読まず直感で操作。誤クリック・空送信・連打
- P2 ベテラン：キーボードで高速・大量入力。Tab遷移・IME変換中のEnter
- P3 悪意：境界値・不正値・権限外・二重送信
- P4 データ整合：画面でなく裏のDBテーブルを直接確認
- P5 移行：旧データを投入。欠損・異形式・文字コード・件数
- P6 回帰：今まで動いていた周辺機能が壊れていないか
- P7 仕様懐疑：実装を信用せず、一次情報（仕様）と挙動を突合
```

## 新機能と移行で作り方を分けた

個人的にいちばんの気づきはここでした。  
同じ「テストケースを作る」でも、仕様の出どころが違うと、作り方も正解の基準も変わりますし、最初は1つのスキルで両方を捌こうとして、出力がちぐはぐになっていました。  
なんとかせねばと思い、2本に分けることにしました。

| 観点 | 新機能用 | 移行用 |
| --- | --- | --- |
| 仕様の出どころ | 課題（PBI）＋ ソースコード | 既存仕様の正本（ヘルプセンター）＋ デザインパターン |
| 正解の基準 | 要件を満たしていること | 仕様どおりに動いていること |
| 主役ペルソナ | P1〜P7（特にP3悪意・P4データ整合） | P5移行担当 ＋ P7仕様懐疑者 |
| 出力 | テストケースCSV | テストケースCSV ＋ 要件カバレッジ表 ＋ 設定パターン表 |

図にするとこうです。入口は同じ「テストケースを作りたい」でも、仕様の出どころで分岐します。

<iframe src="https://embed.zenn.studio/mermaid#zenn-embedded__309a60f4607ab" frameborder="0"></iframe>

新機能用は、こういう順番で進めます。

1. 「課題の受入条件を満たすか」を見る
2. 該当箇所のソースコードを読みにいく
3. 期待結果に、実際のテーブル名・カラム名を書き込む

移行用は発想が逆です。要件を起点に「何をテストすべきか」を考えるのではなく、既存仕様の正本を起点に「仕様どおりに動くか」を1件ずつ確かめにいきます。

1. 画面ごとの業務仕様（社内のヘルプセンターに載っています）の記載どおりに動くかを、1件ずつ確認する
2. 画面をまたいで共通するUIの挙動（一覧のTab/Enter移動、行の追加・複製・削除など）は、機能ごとに書くと重複するので、あらかじめデザインパターンとして切り出しておく
3. 切り出したデザインパターンも、画面ごとの仕様と同じように、そのとおり動くかを確認する

受注の移行ではこのやり方で、200件を超えるテストケースを作りました。新機能のつもりで移行を設計すると、「要件は満たすけれど既存の仕様とはズレている」ケースを取りこぼすので、分けて正解でした。

## CSVの設計（25列とISO 25010）

スキルが出力するのは25列のCSVです。

区切り文字はセミコロン、セル内の改行は `<br>` 、文字コードはUTF-8で固定しています（テストタイトルや期待結果に「、」が入っても列がずれないように）。

```
要件ID;要件説明;Test Basis;テストケースID;テストタイトル;優先度;テストタイプ;品質特性（ISO25010）;リスク;テスト観点;Test Data;前提条件;実施画面;操作手順;期待結果;コードモジュール;自動化(YES/NO);自動化優先度;回帰テスト対象(YES/NO);最終更新日;結果;内容;エビデンス;テスター;テスト実施日
```

品質特性に ISO/IEC 25010 を使っているのは、「なんとなく網羅した気になる」のを避けるためです。機能適切性・性能効率性・互換性・使用性・信頼性・セキュリティ・保守性・移植性、という語彙を必ず埋めさせることで、観点の偏りが見えるようになります（これは2011年版の8特性。2023年版では「安全性」が加わり9特性になっています）。

実際の1行はこんな感じです（値はダミーです）。

```
PBI-XXX-06;フィルタ条件がDropDown型のとき選択肢が前面に表示されること;PBI-XXX;TEST-XX-001;受注一覧：フィルタの選択肢が前面に表示される;高;機能テスト;使用性;選択肢が背面に隠れるとフィルタ操作ができなくなる;UI/UX;受注データが登録済みであること;ログイン済み・受注一覧を表示済み;受注一覧;1. 受注一覧を開く<br>2. フィルタアイコンをクリック<br>3. DropDown型の入力欄をクリック;選択肢一覧が前面に表示され、クリックで選択できること;（フィルタUIのコンポーネント）;NO;C:不要;YES;2026-04-14;未実施;;;;
```

テストの工数感は、1・3・5・8の4段階スコアで表して、自動化と回帰テストの判断に紐づけています（1＝文言修正のみ／8＝DB構造の変更・全体への影響あり）。

## 根拠のないケースを出させない

AIにテストケースを作らせるうえで、いちばん気をつけたのは、それらしいけれど根拠のないケースを出させないことです。テスト設計と同じで、偽陽性を出さないのが大事でした。

- Test Basisの列に一次情報を引く。新機能なら課題番号、移行なら「ヘルプ記事のどの見出しか」を、節まで書かせる。独自の採番はせず、公開されている見出しをそのまま引用する。
- コードを確認できていない箇所は、推測で埋めず、コードモジュールの欄に「※要静的解析（未実施）」と正直に書かせる。
- 要件はテスト可否で仕分ける。移行では全要件を洗い出したうえで、「テスト可／テスト可（保留：実装が未検出）／テスト不可（仕様が不足）」に分類し、要件カバレッジ表として別CSVに残す。「仕様がないから書けない」を要件のギャップとして見えるようにするためです。

「分からないことは分からないと書かせる」。地味ですが、これがいちばん効きました。

## master と artifacts の二層管理

成果物は2層で持っています。

- `master/{機能}.csv` … 生きた正本。今どのケースが有効かを一覧でき、次の課題で採番を続けられる。使わなくなったケースは消さず「DEPRECATED」と印をつけて、履歴を残す。
- `artifacts/YYYY-MM/...` … 課題・移行ごとのスナップショット。「あのとき何をテストしたか」を後から遡れる。

スプレッドシートやエクスポートは、この2層から派生させるものであって、正本ではない、という整理にしています。

## スプレッドシートへの書き出し

レビューや実施はチームでやるので、最終的にはGoogleスプレッドシートにします。CSVを、サマリ表紙付きの1冊に変換するスキルを用意しました。1ページ目に件数・実施率・不具合率・カバレッジ率・対象範囲の表を置き、以降に全テストケースや要件カバレッジを並べます。

![](https://static.zenn.studio/user-upload/a39a9b92a41c-20260622.png)

*▲ サマリ表紙の例。件数・優先度内訳・実施率・不具合率・要件カバレッジ率・設定カバー状況までを1ページで俯瞰できる。*

ここは社内ルールと直結する部分です。個人情報や機密情報は外部サービスに送らないことになっているので、Driveにアップロードする前にテストデータの列を走査して、顧客名・メール・電話番号などが混ざっていないかをチェックし、確認なしには外に出さないようにしています。

## 使い方

入口が違うので、トラックごとに流れも分かれます。

**新機能トラック** （仕様の出どころ＝課題＋ソースコード）

```
# 1. 設計に入っていいか判定
/pbi-review PBI-XXX

# 2. テスト計画書を作成して課題管理ツールに起票
/test-plan-creation PBI-XXX

# 3. テストケースCSVを生成し、台帳に追記
/test-case-creation PBI-XXX

# 4. 品質レビュー（指摘のみ。修正はしない）
/test-case-review （作成したCSVのパス）

# 5. サマリ表紙付きスプレッドシートに変換
/gsheet-export
```

**移行トラック** （仕様の出どころ＝Kブック＋デザインパターン）

PBIがないので `pbi-review` や計画書は通さず、ヘルプ記事を起点にテストケース作成から始めます。

```
# 1. ヘルプ記事（Kブック）を起点にテストケースCSVを生成
/migration-test-creation （ヘルプ記事のURL）

# 2. 品質レビュー（指摘のみ。修正はしない）
/test-case-review （作成したCSVのパス）

# 3. サマリ表紙付きスプレッドシートに変換（要件カバレッジ表も同梱）
/gsheet-export
```

入力は、課題管理ツール（Backlog）のMCP連携で課題番号を渡すだけです。ちなみに、以前は課題の説明文をコピペしていて、古い版を貼ってしまったり貼り忘れたりすることがあったのですが、それがなくなりました。期待結果のテーブル名・カラム名の確認は、自作のMCPでClaudeが直接スキーマを見にいくので、打ち間違いも消えました。

## やってみてわかったこと

- 「やらないこと」を明示すると、スキルが安定します。「テストレビューは修正しない」「コードを確認できていない箇所は埋めない」といった制約が、AIの越権やでっち上げを抑えてくれました。
- 仕様の出どころでスキルを分けると、作り方の軸がぶれません。新機能と移行は別物でした。同じプロンプトで捌こうとしたのが、そもそもの間違いでした。
- フォーマットは厳格に決めておくほうがいい。列の構成・区切り文字・改行のルールをスキルに明記してから、スプレッドシートへの取り込みが無修正で通るようになりました。
- AIはテスターではなく「テスト設計者」として使う。観点の網羅とCSVの構造化まではAIに、実行と合否の判断は人間が。一人でQAを回すには、この分担がちょうどよかったです。

## これからやりたいこと

- 「似た課題の過去ケースを参照して設計する」機能の追加

## おわりに

AIで「テストケースを作る」こと自体は、もう難しくありません。難しかったのは、観点を毎回そろえて網羅することと、文脈ごとに作り方を切り替えることでした。

その2つは、プロンプトを書き直し続けるより、7人のペルソナと、新機能用・移行用に分けたスキル、という仕組みに固定してしまうほうが効きました。やってみていちばん面白かったのは、「何をテストするか」を考えるテスト設計の発想が、「AIに何をやらせて、何をやらせないか」を決めるスキル設計に、そのまま使えたことです。

ちなみにこの記事を書いている途中で、自分が品質特性をISO 25010の「8特性」のつもりで使っていたのが、最新版では「安全性」が増えて9特性になっていることに気づきました。頭の中では網羅したつもりでも、人に説明する形にすると穴が見える。アウトプットがいちばん容赦のないレビュアーだ、というのは、テストケースを書くときとまったく同じでした（スキル側も9特性に直します）。

QAに限らず、業務の定型部分をスキルにしていくときの参考になればうれしいです。
