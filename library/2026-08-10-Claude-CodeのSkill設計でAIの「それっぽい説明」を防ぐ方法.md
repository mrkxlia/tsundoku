# [Claude Code] AIの説明が「それっぽいだけ」で終わる問題を、Skill設計で解決した話
2026-08-11
[NCDC テックブログ](https://zenn.dev/p/ncdc) Publication Pro

## はじめに

以前、新しく参画するプロジェクトのキャッチアップに、AIを使ったことがあります。

「このリポジトリを読んで、アーキテクチャをまとめて」と気軽にお願いしたら、それらしいレポートが思ったより早く出てきました。

ただ、実際に読んでみると

> 「ECSでバックエンドを動かしています」

これで終わりました。

いや、それは知ってる。

聞きたいのは「じゃあどう動いてるの？」の方です。ALBを経由しているのか、セキュリティグループはどう制限されているのか、そこが全然分からず知りたい情報に辿り着けませんでした。

読んだ気にはなるのに、次の作業に進めるだけの具体性が一切ない。

今回、自分用に「案件キャッチアップ」を助けるClaude Code Skillを作る中で、この「それっぽいだけ」問題に対する自分なりの解決策が見えてきたので、整理しておこうと思います。

## なぜ抽象的になってしまうのか？

少し考えてみた感じだと、これはAIが手を抜いているというより、 **「どのレベルの具体性で書けばいいか」を誰も指定していない** だけだと感じました。

「アーキテクチャをまとめて」という指示だけでは、AIからすると「ECSで動いています」も「ALB→ECS→Auroraの流れで、セキュリティグループが〜」も同じくらい「まとめ」として正解になってしまう。

つまり、抽象と具体のどちらで答えるべきかの判断をAI任せにしていた、というのが根本原因でした。

「だったら、その判断はこちらで縛ってしまえばいい」

いろいろ試して、調べた結果、上記が今回たどり着いた発想です。（正直具体的に書きすぎるのは面倒なので、「こんなことが書きたいんだけど、具体例を出して」のようにAIに指示する文章をAIに出させるようなことをしています）

## 「良い例・悪い例」で具体性のレベルを縛る

### 実際に使っている悪い例・良い例

やったことは実はシンプルで、Skillの指示文の中に「このレベルでは不十分」「このレベルまで書く」という対比を、実際の文章の形でそのまま埋め込みました。

例えばDB設計を説明させるパートでは、こんな感じにしてみました。

悪い例（抽象的すぎる）:

> 「 `Member` テーブルはメンバー情報を管理します」

良い例（このレベルまで求める）:

> 「 `Member` テーブルは組織に所属するユーザー1人を表し、 `role` カラムでMANAGER/USERを区別します。MANAGERは組織のメンバー招待・削除ができ、USERは閲覧・操作のみです。ログインはCognitoが担当しており、Cognitoのユーザー名と `Member.email` を照合してプロフィールを引いてくる設計です。」

同じように、インフラ構成の説明パートにもこの対比を入れています。

悪い例:

> 「ECSでバックエンドを動かしています」

良い例:

> 「ECS Fargateでバックエンドのコンテナを動かしています。ALB（ロードバランサー）→ECS（コンテナ）→Aurora（DB）という流れでリクエストが流れ、ECSのセキュリティグループはALBからの通信しか受け付けないため、ECSに直接アクセスすることはできません。」

### なぜこの縛り方が効くのか

「具体的に書いて」と一言お願いするより、こうして「ここまでは不十分」という下限を実例で示す方が圧倒的に効くというのが実感でした。

正直、これは理屈で分かっていたというより、実際に使ってみてから後で気づいた部分でもあります。

抽象的な指示は解釈の余地が大きいですが、悪い例そのものを見せられると「ああ、これじゃダメなんだな」というラインが的確に伝わっている感覚がありました。

さらに、Skillの冒頭には「レポートを読み終えた後、あたかも自分がそのプロジェクトの実装者であるかのように振る舞えるレベルの理解を提供すること」というゴールも明記しています。

抽象的な「ちゃんと書いて」ではなく、「読んだ後に何ができるようになっているべきか」という **到達点そのもの** を言語化しました。そうすることで、AIが自分で「これくらい具体的に書かないと目標に届かないな」と判断できるようになった感覚があります。

## 文章だけでは足りない ── 図を必須にした設計判断

### mermaid図・ASCII図を必須にした理由

良い例を仕込んだ後も、まだ一つ引っかかる部分がありました。

テーブル同士の関係や、リクエストがどのガード・コントローラー・サービスを通っていくかというような「流れ」は、文章でどれだけ具体的に書いても、正直読みにくい。

文章は基本的に上から下に読むものなので、分岐や依存関係を表現するのに向いていないと思っています。

なので文章の密度をどれだけ上げても限界があって、表現形式そのものを変えるしかないなと考えました。

そこで、そういった「流れ」や「関係」を扱うパートでは、 **mermaidやASCII図での出力を必須** にしました。文章だけで済ませることを許さない、という設計にしました。

### 実際の出力例

例えば、リクエストがどう処理されるかは、こんな図で出させています。

```
HTTP リクエスト
    │
    ▼
[Guard: JwtAuthGuard]（JWT検証 → memberを取得してrequestにセット）
    │
    ▼
[Guard: PermissionValidationGuard]（権限チェック）
    │
    ▼
[Controller] → [Service]（ビジネスロジック・DBアクセス）
    │
    ▼
HTTP レスポンス
```

テーブルの関連はmermaidのER図で出させます。

これを見て「当たり前では」と思うかもしれませんが、 **「図で出せ」ではなく「この種類の情報は図でなければ出力を認めない」くらいまで踏み込んで指示する** のがポイントでした。

「文章でも図でもいいので分かりやすく」だと、結局AIは楽な方（文章）を選びがちです。

## この考え方は他のSkillにも応用できる

ここまでの話はキャッチアップ用のSkillに限った工夫ではなく、 **AIに何かをまとめさせる・説明させるタイプのSkill全般に応用できる** 気がしています。

まだ全部のSkillで試せたわけではないので、あくまで感触ベースですが、整理すると、やったことは2つだけです。

1. 「これでは不十分」という悪い例と、「ここまで書いてほしい」という良い例を、指示文の中に実物として埋め込む
2. 文章では表現しにくい情報（流れ・関係・分岐）は、図での出力を必須にする

どちらも「もっと具体的に」「分かりやすく」という抽象的なお願いを、 **実例と形式の指定** という具体的な縛りに置き換えているだけです。

当たり前のようで、Skillを作り始めた当初の自分はここに気づかず、ふわっとした指示文で満足していました。

## まとめ

AIに何を書かせるかを考えるとき、つい「何をやらせるか」ばかりに意識が向きがちですが、実際に効いたのは「どのレベルの具体性で、どんな形式で書かせるか」まで踏み込んで設計することでした。

- 指示は抽象的なお願いではなく、実例で示す。
- 文章で伝わらないものは、形式ごと変えてしまう。

この2つを意識するようになってから、AIに何かをまとめさせるたびに感じていた「それっぽいけど使えない」というモヤモヤが、かなり減った気がしています。（気だけかもしれないが今はよしとします）

とはいえ、これで「はい！完璧！！」というわけでもなく、何か引っかかるところがあれば、徐々に改善しながら育てていこうと思います。
