# ３年動いている業務アプリを、AI4人がかりで作り直したお話
2026-08-11
3年動いている車両管理アプリがあります。Power Apps のキャンバスアプリで、画面数は24。中身の話はこの記事の主題ではないので、 **「そこそこ育ってしまった業務アプリ」** くらいに思ってもらえれば十分です。

直したいところは山ほどありました。でも毎年、見送っていました。理由はいつも同じ2つです。 **壊したら困る。24画面を並べ直す気力がない。**

今回それをやりました。確かめたかったのは、AIが賢いかどうかではなく、 **最新のAIを何体か並べたら、この規模の作り直しが実際に回るのか** です。結論から言うと回りました。ただし、回った理由は予想と違いました。

結論：キャンバスアプリは、いつのまにかテキストになっていた。17画面ぶんのYAMLを1ファイル16,798行にまとめて、Studio に1回貼るだけで画面が入った（これは公式に文書化された一括投入機能ではなく、今回の検証環境で確認できた実測です）。  
そして、この方式でいちばん効いたのは「AIに書かせること」ではなかった。 **書かせるAIと、それを見張るAI・見張るスクリプトを分けたこと** だった。

### 今回使った道具

先に道具立てを並べておきます。 **基本は全部、公式または公式マーケットプレイス提供のものです。** 1つのAIに全部やらせるのではなく、工程ごとに違う道具を当てています。

- **Microsoft 365 Copilot**  
	社内のファイルと会議記録から改修方針と優先順位を出す
- **Power Apps Studio のコード ビュー**  
	YAMLの貼り付け口。実装の本番はここ
- **キャンバス アプリ プラグイン** （キャンバス アプリ作成 MCP サーバー／プレビュー）  
	コントロール定義とデータソースの取得、YAMLの検証
- **Power Automate プラグイン** （ **FlowAgent** MCP サーバー）  
	フロー定義の読み取り。上と合わせて Microsoft の `power-platform-skills` マーケットプレイス提供
- **Claude Code（Opus 5）**  
	書く係。出たばかりの最新モデルで、17画面ぶんを一気に書かせた
- **Claude in Chrome**  
	見る係。ブラウザを操作して実物を確認させる
- **VS Code ＋ Node.js**  
	ローカルの作業場所

キャンバス アプリと Power Automate の2つのプラグインは、同じ Microsoft のマーケットプレイスから入ります。真似したい人向けに、入れ方だけ置いておきます。

/plugin marketplace add microsoft/power-platform-skills  
/plugin install canvas-apps@power-platform-skills  
/plugin install power-automate@power-platform-skills

ざっくり言えば、 **要件を出す係・書く係・見張る係・実物を見る係** を全部バラバラの道具にした、という話です。

ただし、これで終わりませんでした。「見張る係」を公式ツールだけで完結させようとして、後半でつまずきます。そこで初めて自分でも道具を書くことになるのですが、それは最初から計画したものではなく、 **失敗のたびに後から生まれた結果物** です。順番どおり話します。

今回の規模  
画面　　　24 → 17（統合後）  
貼り付け　16,798行を1回  
コントロール名　952件・重複ゼロ  
照合した列　89件  
名前付き数式　70件  
App.OnStart の変数　54件  
数式エラー（原因はセミコロン1個）　213件  
アクセシビリティ指摘　73件 → 0件

## 1\. 何を直すかを、自分で決めなかった

最初にサボりました。要件を書かず、Microsoft 365 Copilot に社内の記録を読ませたんです。対象はファイルと外部情報が1,685件、会議が12件。そこから優先度つきの15項目が出てきました。

で、その優先順位が自分の感覚と全然違った。

自分の第1位は「見た目が古い」でした。記録から出てきた結論には、 **「見た目だけの全面刷新」がはっきり“見送り”に分類されて載っていました。** ぐさっときました。でも正しい。

最優先に上がってきた3件は、業務の細部は違うのに全部同じ形をしていました。 **入力の食い違いが、誰にも気づかれないまま残る** ——それだけです。見た目は最後でいい、というのはそういう意味でした。

要件を「自分の不満」から作ると、いちばん目につくものが1位になります。「記録の総和」から作ると、いちばん困っているものが1位になる。AIに読ませる価値は、賢い提案よりも **この順番のズレを見せてくれること** にありました。

## 2\. キャンバスアプリは、いつのまにかテキストになっていた

ここ数年で前提が変わっています。キャンバスアプリのソースコードは `.pa.yaml` という人間が読めるYAML形式で、画面ごとに1ファイルに分かれて保存されています。Studio 上でコントロールのコードを見て、コピーして、貼って新しいコントロールを作る「コード ビュー」は、2024年6月にパブリック プレビュー、2025年3月に一般提供として公開されています。

### 形式の世代交代でつまずく

最初につまずいたのはここです。AI側が出してきたのが、 `pac canvas unpack` 相当の `.fx.yaml` 形式でした。貼るとこうなります。

error PA1001: Property 'scrTripStart As screen' not found on type  
Microsoft.PowerPlatform.Formulas.Tools.Schemas.SchemaV3.PaModule

お分かりでしょうか。 **答えがエラー本文に書いてあります。** 求められているスキーマのバージョンが型名に出ている。ここを読み解くまでに30分かかりました。

公式には `.fx.yaml` も、プレビュー期のコード ビュー形式も「廃止」と明記されていて、アクティブなのは `.pa.yaml` だけです。ただ **世に出回っているサンプルは旧形式がまだ多く、AIもそちらを引いてきます。** 形式は最初に明示してやる必要がありました。

実は一般提供の告知そのものに、その伏線があります。「プレビュー期に貼ったコードは、新しい形式に更新することを推奨する。もう一度 Studio に貼り付け、コピーし直して、GA版として保存してほしい」と書かれていました。旧形式のスニペットがネット上にまだ残っている理由は、この移行がユーザー任せだったからのようです。

### ここは線を引いておきます

公式ドキュメントは `.pa.yaml` について「読み取り専用であり、アプリの読み込み中は使用されません」「外部編集・マージ・競合の解決は Power Platform Git 統合でのみサポートされます」と明記しています。つまり **ファイルを直接アプリに食わせる使い方は想定されていない** 。

今回やったのは、その形式でテキストを書いて **コード ビューの「コードの貼り付け」から取り込む** ことです。貼り付けは公式に用意された経路で、コードは新しいコントロールが作られる前に検証されます。ここを混同すると話が変わるので、分けておきます。

## 3\. MCP経由の生成・検証を通したのに、Studio には空の画面が現れた

当初はキャンバスアプリ用のMCPサーバー経由でコントロールを組んでいました。AIコード生成ツールからアプリを作ったり編集したりできる仕組みで、公式にはプレビューとして案内されています。前提として「Studio でアプリを開き、共同編集を有効にする」と書かれているので、そこは有効にしてありました。

その状態で、生成とYAMLの検証を通して出来上がったのがこれです。

![](https://cdn-ak.f.st-hatena.com/images/fotolife/P/PowerDaaps/20260726/20260726191737.png)

作り直す前の入力画面。コンテナが黒く塗りつぶされ、見出しと本文が重なっている。選択欄も「テキスト入力」のまま（アプリ名・ユーザー名はマスク済み）。

業務アプリを頼んだのに、抽象画が出てきました。

ここが今回いちばん厄介だったところです。 **検証は通っています。** コントロールはツリーに並んでいる。画面も開ける。エラーも出ない。ただ絵が壊れている。

この見え方だと、まず疑うのは自分が書いたレイアウトです。だから座標を直し、コンテナを組み替え、色を指定し直す——という直しを5回やりました。ぜんぶ外れでした。 **直す場所そのものが存在しなかった** からです。

## 4\. 原因は、Studioに反映される途中で値が抜けていたことだった

行き詰まって、Claude in Chrome にブラウザの Studio を開かせました。黒い矩形を選択させて、右のプロパティ パネルを読ませる。返ってきた答えがこれです。

**位置・サイズ・色、すべて「値なし」。**

つまり、この検証環境では **コントロールの名前と階層はStudioに反映された一方で、確認したコントロールのプロパティ値は一つも書き込まれていませんでした。** 黒く見えていたのは `Fill` が未指定だったからで、レイアウトの計算ミスではありません。5回の手直しは、全部「まだ書き込まれていない値」を直そうとしていたわけです。

MCPサーバー側の `compile_canvas` は、公式リポジトリの説明では「ディレクトリ内のYAMLをPower Appsのオーサリング サービスで検証する」ツールです。検証と、Studioへの反映は別の工程なので、値が抜けた原因をこの1関数だけに絞り込むことはできません。ここでは「MCP経由の一連の工程のどこかで、値がStudioまで届いていなかった」という観測にとどめておきます。

手元のYAMLは正しく書けていました。 **正しいYAMLが、届いていなかっただけ** です。

念のため書いておくと、これはプレビュー機能で観測した挙動なので「そういう仕様」という話ではありません。原因の候補も一つに絞り切れていません。このMCPサーバーのプラグイン付属の手引きには、 **Studio のブラウザ タブをセッション中ずっと開いたままにする必要があり、閉じると共同編集セッションが終了して、コンパイルと状態同期の両方が壊れる** と書かれています。作業中にタブの状態を完全に制御できていたかは、今となっては確認しようがありません。セッションの持ち方が原因だった可能性も残る、というのは公平のため書いておきます。

ただ、教訓のほうは原因に関係なく残ります。 **「成功」と返ってくる処理が、実は半分しか仕事をしていないことがある。** そして半分しかやっていないことは、出力の内側からは見えない。

見えたこと 1

### プロパティが空だった

黒い矩形を選択させ、位置・サイズ・色が「値なし」であることを確認。原因がレイアウトではなく書き込み自体だと分かった。

見えたこと 2

### 数式エラー213件

App チェッカーの「数式」に213件。ファイル上のYAMLはどのチェッカーも通っていたので、Studio を見るまで存在に気づけなかった。

213件の原因は、名前付き数式 `nfNav = Table(...)` の末尾のセミコロン1個でした。App の `Formulas` プロパティは定義をセミコロンで区切って並べる仕様なので、1文字抜けると **以降の定義がまとめて前の式に飲み込まれます** 。70個の定義が1個の巨大な式になっていました。

ここが今回いちばん学んだところです。テキストの世界で完結している限り、この2つはどちらも見つかりません。 **自分の答案を自分で採点させると、だいたい丸をつける。** 別の視点から実物だけを見る係が必要でした。

## 5\. 方針転換：16,798行を1回で貼る

MCP経由の組み立てをやめて、全部「貼り付け」に切り替えました。`.pa.yaml` は `Screens:` の下に画面を何枚でも並べられるので、17画面ぶんを連結すれば1ファイルになります。

貼り付けたもの  
SCREENS\_貼付用.pa.yaml　16,798行　画面17枚（Screens: 配下のみ）  
  
数式バーに直接貼ったもの  
App\_Formulas\_貼付用.txt　名前付き数式 70件  
App\_OnStart\_貼付用.txt　　変数 54件

分けている理由があります。公式のコード ビューの既知の制限に「 **App Object のコードをコピー＆ペーストしたり、表示したりすることはできません** 」と書かれているとおり、貼り付けで入れられるのは画面だけです。App の `Formulas` と `OnStart` は対象外なので、数式バーへ直接貼ります。

ここで一つ、正確に言っておきたいことがあります。公式ドキュメントが説明しているコード ビューの貼り付けは、あくまで **選択したコントロールとその子コントロールのコード** を対象にしたものです。今回のように `Screens:` の下へ17画面ぶんを並べて丸ごと貼る、という使い方そのものは文書化されていません。

**①コントロール単位の貼り付けが公式の手順**

**②その入り口に17画面分の `.pa.yaml` を流し込んだのが今回の実証**

——ここは分けて理解してください。

もう一つ、公式には「コードを貼り付けるにはブラウザのクリップボード アクセスが必要」とあり、初回は権限ダイアログが出ます。ここで許可しないと静かに何も起きません。

![](https://cdn-ak.f.st-hatena.com/images/fotolife/P/PowerDaaps/20260726/20260726191928.png)

作り直したあとの同じ画面。1〜4の手順に分け、選択欄はドロップダウンになった。この時点のツリー ビューは13画面（このあと4画面を足して、最終的に17画面になる）。

### レスポンシブをやめた

画面設計は 1366×768 の固定サイズに割り切りました。パソコンからしか使わないアプリなので、絶対座標で置いたほうが崩れない。

そして絶対座標にすると、副産物が出ます。 **はみ出しと重なりが、計算で検出できるようになる。** これが次の話です。

### ここは素直にモデルの世代だと思う

1つ書き添えておきたいことがあります。書かせたのは出たばかりの **Claude Opus 5** です。17画面ぶん・16,798行を通しで生成させても、画面をまたいだ命名規則も座標の体系も崩れませんでした。

数千行あたりで前半の約束を忘れる、というのが以前の感覚だったので、ここは正直に世代が上がった効果だと思っています。逆に言えば、 **この規模を一息に書ける道具が出てきたから、この進め方が成立した** ということでもあります。

## 6\. 出力の量が人の確認能力を超えたら、確認を機械にする

17画面を目で確認するのは無理です。だから画面を生成するスクリプトと一緒に、8種類の検査を書きました。1画面直したら必ず全部通す。

■ 生成 → 17画面  
■ 装飾要素の補完　　矩形→ラベル変換 36件 / アイコンのラベル付与 16件  
■ YAML 構文　　　　　構文の問題なし  
■ 幾何　　　　　　　はみ出し 0件 / 重なり 0件（17画面）  
■ コントロール名　　952件 / 重複なし  
■ 列名　　　　　　　照合した列 89件 / 問題のある画面 0件  
■ 名前付き数式　　　定義済み 70件 / 未定義参照 0件  
■ App.Formulas　　　定義 70件 / OnStart変数 54件 / 問題なし  
  
全チェック通過

この8種は、ぜんぶ **実際に踏んだ失敗** から生まれています。つまり最初から設計したものは一つもありません。

失敗から

### コントロール名の重複

別の画面で同じ名前を使って `PA2110 already exists` 。名前はアプリ全体で一意でなければならない。以後952件を毎回照合。

失敗から

### 存在しない列名

SharePoint に無い列を4つ参照していた。列の実体をJSONに落として、89列と毎回突き合わせる検査を足した。

失敗から

### YAMLの書き方

ブロックスカラーの字下げ、式が `=` で始まっていない、逆に `==` になっている、平文に `": "` が混ざる。全部一度は踏んだ。

失敗から

### セミコロン1個

213件を生んだ1文字。括弧の対応とセミコロンの有無を機械で数えるようにした。人間は数えられない。

生成AIに大量のコードを書かせる作業の要点は、書かせる側ではなく **受け取る側** にあります。出力が人間の確認能力を超えた瞬間、確認を機械化しないと量のメリットが丸ごと消えるからです。

## 7\. チェッカーが0になっても、それが「正しい」とは限らない

App チェッカーのアクセシビリティが73件出ました。ここで、公式のガイドラインどおりに直したのに、減りませんでした。

Power Apps のアクセシビリティ ガイドラインには、こうあります。

Label・Image・Icon・Shape コントロール：操作対象として使うなら `TabIndex` を0に。 **そうでないなら -1 に。** （公式ドキュメント「Create accessible canvas apps」より）

今回直したかったのは、区切り線や色帯として置いていた装飾用の矩形（Rectangle）と、ブランドアイコンです。どちらも操作対象ではありません。だから公式どおりに、こう直しました。

- 1回目： `TabIndex` を `-1` 、 `AccessibleLabel` を空に。ガイドラインどおりの「非操作」設定——減らない
- 2回目： `DisplayMode.View` を足す。表示専用にする設定で、これでキーボード操作から外れると思っていた——減らない

2回目は、あとで調べ直すと前提が誤りでした。公式にキーボード ナビゲーションから除外されると明記されているのは `Visible: false` か `DisplayMode.Disabled` の場合で、 `View` はその代わりになりません。狙いを外した施策を積み重ねていたわけです。

ここで気づきました。 **この検証環境の App チェッカーは、Rectangle と Icon（Classic）というコントロールの種類そのものを「操作できる要素」とみなしていて、TabIndex や DisplayMode をどう設定しても免除されませんでした。** 公式のチェッカー仕様には「指摘の対象は **対話型コントロール** ――本質的にそうであるか、OnSelect が設定されている、あるいは TabIndex が0以上といった対話型の性質を持つもの」とあります。Rectangle も Icon も、そもそも OnSelect を持てるコントロール種別です。今回の観測は、この仕様の書き方から外れてはいませんでした。

直した方法は、値の調整ではなく **コントロールの種類を変えること** でした。装飾用の矩形は Label に置き換える（Label は同じ指摘を受けない）。

アイコンのほうは、正直に書くと一枚岩ではありません。押せる選択マークのアイコンには `TabIndex: 0` と意味のあるラベルを与えました。これは公式ガイドラインの「操作対象として使うなら0にする」に沿っています。一方、ヘッダーの純粋な飾りであるブランドアイコンにも同じ処理を機械的にかけていて、本来なら `TabIndex: -1` と空のラベルが正しいはずです。矩形と同じように Label へ置き換える手もありましたが、今回はそこまでやらず、 **チェッカーを黙らせる側を選びました。** 褒められた設計ではありません。

73件が0になったのは事実ですが、これで「アクセシビリティ的に正しくなった」と言い切るのは早すぎます。 **App チェッカーの指摘が0件になったことと、実際のスクリーンリーダーで使いやすいことは別の話です。** 今回、実機での読み上げ検証はしていません。チェッカーを信じすぎるな、というのは6章と同じ教訓です。

## 8\. リストは、仕様書ではなく実装を読ませて作った

新スキーマ用に SharePoint リストを6つ、列は合計89。画面でぽちぽち作るのは嫌なので、以前作った「CSVを設計書にしてリストを作るフロー」の v2 を使いました。

ここでも使い方を変えています。フローの説明書を読むのではなく、 **Power Automate のフロー定義そのものをMCP経由で読ませて、実装から入力契約を導出させました。** 以下はPower Platform全般の制約ではなく、この自作フロー v2 が受け付ける入力条件です。

- 扱える型は11種類
- 日付型は `yyyy-MM-dd` の **10文字ちょうど** でないと弾かれる
- CSVのどこにもダブルクォートを入れてはいけない
- `unique=true` は `required=true` とセットでないと通らない

私が最初に書いたCSVは `date` 型にISO形式の日時を入れていたので、投げた瞬間に落ちる代物でした。 **仕様書ではなく実装が仕様** という当たり前のことを、AIに読ませて先回りできたのが大きい。

![](https://cdn-ak.f.st-hatena.com/images/fotolife/P/PowerDaaps/20260726/20260726192053.png)

リスト作成フローの実行結果。縦に細長く伸びているのが、型ごとの分岐を含むアクションのグラフ。「ご利用のフローが正常に実行されました。」（URLは切り落とし済み）

なお、リストの作成そのものは自分の手で実行しました。 **MCPからリストを直接作らせない** のは今回ずっと守ったルールです。既存の本番リストも参照専用にして、書き込みは一切させていません。

### PDFのところは公式の注意が多い

帳票の出力には `PDF()` 関数を使いました。ここは公式に注意書きが並んでいる領域なので、使うなら先に読んでおいたほうがいい場所です。

- 実験的機能。既定でオフで、設定から有効にする必要がある
- 生成はアプリが動いている **端末側** で行われる。端末の能力に依存する
- 極端に大きいファイルを作るとアプリがクラッシュしうる
- 入れ子のギャラリーは非対応
- `PDF()` を呼び出した **その画面上にあるコンテンツからしか** 生成できない

最後の制約が、今回の設計に効いています。 `ExpandContainers` オプションを使えば表示しきれない内容を展開する道もありますが、今回は **現在の画面上だけを対象にする制約** と帳票のレイアウトを踏まえて、1ページぶんずつ区切って複数のPDFに分ける形を選びました。

### 粗さも残っています

2枚目の画像、数値の1つが **「0. L」** と表示されています。書式に `#,##0.#` を使っているせいで、値が0のとき小数点だけ居残る。以前べつの書式の不具合を直したときの取りこぼしで、まだ直していません。

完成と言えるところまでは来ていない、という意味でそのまま載せておきます。

### 実装から仕様を読む

フロー定義を直接読ませて、CSVの入力契約を導出。説明書より実装を信じられるようになった。

### 使ってみた実感（個人の感想です）

公式の仕様の話ではなく、4日間さわった側の評価です。かなり率直に書きます。

- **Claude Opus 5 — コード生成能力はピカイチ。** 今回の主役です。この規模を一息に書けるモデルが出たから、この進め方が成立しました
- **Claude in Chrome — 自分の眼のように見てくれる。** 「あの画面を開いて、あのコントロールを選んで、プロパティを読んで」が通る。手も目も貸してもらっている感覚に近い
- **FlowAgent MCP — 好きなフローを自由自在に作れるので素晴らしい。** 今回は読み取りに使いましたが、作る側でも効きます。ここは文句なし

コツは「作らせる」と「見る」を別のAIに割ることでした。同じ文脈を持ったAIに自己検証させると、自分の間違いを正当化する方向に説明が寄っていきます。  
ブラウザ越しに実物だけを見るAIと、ファイルの中身だけを機械的に数えるスクリプト。この2つが外からの目として働きました。

## 11\. この先、アプリは自分を直しはじめる

今回やったことを分解すると、4工程になります。

① 記録から改善点を抽出する  
↓  
② ソースコードを書き換える  
↓  
③ 動いている実物を見て、意図どおりか確認する  
↓  
④ 差分を検査して、壊れていないことを確かめる

この4つ、今回すでに **全部AIとツールがやっています。** 人間が入ったのは、優先順位の承認、リスト作成の実行、そして「これはコントロールの種類の問題では？」という筋の切り替えだけでした。

逆に言えば、残っているのは **判断とリスクの引き受け** です。

だから、それぞれの精度が上がっていった先にあるのは、アプリケーションが自分の改善点を見つけて自分を書き換える方向だと思っています。キャンバスアプリがテキストになったのは、その前提条件が一つ揃ったということです。ソースコードとして読めて書けるものは、自動で直せる対象になる。

もちろん今はそこまで自動にできません。今回も、MCP経由の生成結果と手元のYAMLが噛み合わずに5回空振りし、セミコロン1個で213件のエラーが出て、公式ガイドラインどおりに直したのにチェッカーの指摘が減らないという足踏みがありました。

ただ、それらはどれも **「検査を1本足せば、少なくとも同じ種類の異常を次回から早く検知できる」種類** の失敗でした。ツール側の不備も、自分の思い違いも、外から見る仕掛けを1つ増やせば次からは早く気づけます。失敗が検査に変わっていく速度のほうが、たぶん本体の性能向上より速い。そちらが積み上がる話だと思っています。

3年動いているアプリを止めずに作り直せたのは、AIが賢くなったからというより、アプリがテキストになったからでした。

テキストになったものは、読める。読めるものは、直せる。直せるものは、いずれ自分で直りはじめる。

やればわかるさ。
